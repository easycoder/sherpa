**The two things that shape everything**

1. **Background location is the hard constraint.** A PWA's `watchPosition` is suspended when the app is backgrounded or the screen locks, on both iOS and Android. Recording a walk with the phone in a pocket will have gaps. Design for screen-on recording with a wake lock, aggressive draft autosave, and gap handling — or accept a Capacitor wrapper later for true background tracking.
2. **Google Maps needs a connection.** Tiles can't be cached offline (and caching them isn't permitted). Route data and photos can. If you walk where there's no signal, the basemap must be MapLibre/Leaflet with offline tiles instead. I'd put the map behind a thin adapter so this can change.

**What AllSpeak can and can't do today** — verified against the current runtime and `gmap` plugin:

- `gmap` gives map + markers + centre/zoom/bounds/click. No polyline, no user-position marker.
- The runtime exposes `localStorage`, not IndexedDB. No geolocation, camera, or service-worker vocabulary.
- So the real work is five small JS plugins: `geo`, `photo`, `store` (IndexedDB), `routegeo` (distance/snap/progress), and a map adapter. AllSpeak then owns screens, state and workflow, which is what it's good at.

**Where I'd sharpen your outline**

- "Held in memory" → hold in IndexedDB. RAM dies on refresh or OS kill; a two-hour walk can't live there.
- Record the **full GPS track continuously**, with steps as annotations on it. Without a track there's no line to draw between steps and no path to snap to. A step is a POI; the track is the route.
- Order steps by **distance along the track**, not array index. "Add steps to follow bends" changes the geometry, and distances survive that; indices don't.
- Auto-record needs accuracy and speed filters plus hysteresis, not just a distance threshold, or GPS jitter will create steps while you stand still.
- Store photos separately, compressed and EXIF-stripped, referenced by ID. The old Sherpa put base64 in the blob; don't repeat that.
- "Downloaded" must mean route **and** photos are local and verified before you set off.

**Plan of attack** — the full version is in `PLAN.md`:

- **Phase 0 — walking skeleton:** PWA shell, Google Map, geo plugin, record 10 points + 3 steps to IndexedDB, reload, real-device test with the screen on and off. This answers the background question before anything else is built.
- **Phase 1 — foundation:** data model (`sherpa.route/1`), IndexedDB store, geometry plugin with tests, polyline support, zip import/export.
- **Phase 2 — recorder:** follow-mode map, manual/auto steps, photos, draft recovery.
- **Phase 3 — editor:** metadata, photos, descriptions, links, reorder/insert/delete/reverse.
- **Phase 4 — follower:** route overlay, next-step card, arrival/departure with hysteresis, off-route warning, simulation replay. **This is the MVP: record → edit → follow, offline, one device, file export.**
- **Phase 5 — backend and sync:** accounts, outbox, photo upload, PostGIS nearby queries, share links/QR. Only now does "routes feed each other" become real.

The important sequencing choice: **build local-first and leave the database until Phase 5.** Sync is easy to add to a good local model and painful to retrofit to a bad one.

I don't know IndexedDB: please outline it for me.

**Assistant**

**IndexedDB in one paragraph**

IndexedDB is a transactional, asynchronous object database built into the browser. Each origin (scheme + host + port) gets its own private database. It stores JavaScript values — plain objects, arrays, numbers, strings, dates, `Blob`/`File`, `ArrayBuffer` — keyed by a primary key, with optional indexes for alternate lookups. It is not SQL: there are no tables with columns, no joins, no query language, and no geospatial support. Think of it as a persistent, origin-scoped Map with transactions and secondary indexes.

**The mental model**

[code omitted]

- **Database** — one namespace; opened with a version number.
- **Object store** — roughly a table, but schema-less; each record is a key/value pair.
- **Key path** — the property that holds the primary key (in-line), or you supply the key separately.
- **Index** — a secondary lookup: `routeId`, `updatedAt`, `geohash`. An index can be `unique` or `multiEntry` (one record appears under several keys, e.g. an array of geohash prefixes).
- **Transaction** — a unit of work over one or more stores; `readonly` or `readwrite`. Transactions are serialized and auto-commit when their requests finish.
- **Request** — every operation returns an `IDBRequest`; results arrive via `onsuccess`/`onerror`.
- **Cursor** — how you iterate records or index entries in key order.

In practice, use the `idb` library (a ~1.5 KB promise wrapper by Jake Archibald) so the same operations read as `await db.put('routes', route)`. Dexie is the heavier alternative if you want a query DSL. For Sherpa, `idb` is enough.

**The rules that bite**

1. **Versioning is manual.** Schema changes happen in `onupgradeneeded`, keyed by an integer version. Bump the version, create/delete stores and indexes there, and migrate data. You cannot open with a lower version. Keep a `meta` record with the schema version so the app knows what it is looking at.
2. **Transactions auto-commit.** Do not `await` a network call or a timer inside a transaction; once the request queue is empty, the transaction closes. Do all reads/writes for one logical change in one transaction.
3. **Keys have a type order.** Numbers sort before dates, dates before strings, strings before binary, binary before arrays. Strings sort by UTF-16 code units, not locale. Design keys accordingly.
4. **Values are structured-cloned.** You get a copy, not a reference; prototypes are lost. Functions, DOM nodes and some host objects cannot be stored. `Blob`, `File`, `ArrayBuffer`, `Date`, `Map` and `Set` can.
5. **No SQL, no joins, no geo, no full text.** You get key ranges and indexes. Anything more complex is done in JavaScript after reading records, or with a library (Dexie, `wa-sqlite`, etc.).
6. **Quota and eviction.** Storage is origin-scoped and large but not infinite. `navigator.storage.estimate()` tells you usage/quota; `navigator.storage.persist()` asks the browser not to evict. Persistence is a request, not a guarantee. Safari can clear script-writable storage after periods of non-use; private browsing may be memory-only.
7. **Multiple tabs.** Transactions are serialized, but tabs share the database. Listen for `versionchange` and close old connections; `onblocked` fires when an upgrade waits for an open tab. Use `BroadcastChannel` to tell tabs that data changed.
8. **Async everywhere.** There is no synchronous API on the main thread. Wrap requests in promises, or use `idb`.
9. **Not a backup.** It is a cache and a working store. Export and sync; never let IndexedDB be the only copy of a route someone walked.

**What it is good and bad at**

Good: offline route documents, photo blobs, drafts, an upload outbox, large structured records, per-origin isolation, transactions across stores.

Bad: ad-hoc queries, joins, aggregation, full-text search, geospatial nearest-neighbour, cross-device sync, schema migration ergonomics. For "find the nearest saved location", IndexedDB gives you no help; PostGIS does. On-device you either scan all cached steps (fine for hundreds) or store geohash prefixes and query neighbouring cells.

**How Sherpa would use it**

A single database `sherpa` (version 1) with:

| Store | Key | Indexes | Holds |
|---|---|---|---|
| `routes` | `id` | `updatedAt` | Route document: name, description, track, steps |
| `steps` | `id` | `routeId`, `geohash` (multiEntry) | Flat copy of steps for nearby lookup |
| `photos` | `hash` | `routeId` | `Blob` + dimensions + caption |
| `drafts` | `id` (`"active"`) | — | The in-progress recording |
| `outbox` | `opId` | `nextAttemptAt` | Pending uploads/deletes |
| `meta` | `key` | — | Schema version, user id, last sync |

Two design points matter:

- **Write the route and its outbox entry in one transaction.** Otherwise the tab can close between "route saved" and "upload queued", and the route never leaves the phone.
- **Keep photo blobs out of the route record.** A route document should hold photo IDs and metadata; the bytes live in `photos`. Reading a route then does not drag megabytes through memory, and uploads can be retried independently.

For nearby points on-device, store a few geohash prefixes per step (e.g. precision 6 ≈ 1.2 km, precision 7 ≈ 150 m) in a `multiEntry` index, then query the cell containing the user plus its eight neighbours. For a small number of cached routes, simpler still: read the steps and compute distances in the `routegeo` plugin. The server's PostGIS query remains the real cross-route search.

Because AllSpeak cannot call IndexedDB directly, all of this sits behind `sherpa-store.js`, with a small vocabulary for the app: save/get/list/delete a route, put/get a photo, read/write the draft, enqueue/flush the outbox. The AllSpeak script then never sees a transaction or a cursor — which is the point of the plugin boundary.

**Recommendation**

Start with `idb`, one database, version 1, the six stores above. Request persistent storage when the user starts their first route, show storage usage in settings, and keep export/sync as the real durability story. If the data model later outgrows key/index queries, the escape hatch is SQLite WASM or Dexie — but for routes, steps and photos, IndexedDB is the right fit.

## 22:33

How persistent is IndexedDB? Does it survive a restart?

**Assistant**

**Yes — it survives a restart.** Closing the tab, quitting the browser, rebooting the phone, or the OS killing the PWA does not lose IndexedDB data. It is written to disk, scoped to the origin, browser profile and device.

But "survives a restart" and "permanent" are different questions. By default, IndexedDB is **best-effort** storage. It survives restarts, but the browser may delete the whole origin's data when:

- the origin goes over its quota (you get `QuotaExceededError` on writes, and the browser may evict);
- the device is under storage pressure;
- the site has not been interacted with for a long time (Safari's ITP can apply a roughly seven-day cap to script-writable storage);
- the user clears site data, uses private/incognito mode, or resets the browser.

Private browsing is the clear case: data is usually deleted when the private session ends.

**Persistent mode**

Browsers distinguish two bucket modes:

- **Best-effort** — the default. Persists until quota, storage pressure, inactivity policy, or the user clears it.
- **Persistent** — the origin has requested `navigator.storage.persist()` and been granted it. The browser will not evict it automatically; only the user can delete it (clearing site data, uninstalling, resetting).

[code omitted]

- Chromium (Chrome/Edge) and Safari decide heuristically from engagement — bookmarked, installed as a PWA, notifications granted, regular visits. No prompt.
- Firefox asks the user.
- Safari grants more readily to a Home Screen web app.
- Persistent mode is not a backup: "clear site data" still removes it, and it doesn't sync to another device.

**Writes, crashes and power loss**

A completed transaction (`tx.oncomplete`) is atomic: either all its writes are visible or none are. That is what protects you from half-written routes.

For an ordinary app/browser restart, a completed transaction is there. For a power cut or OS crash immediately after `oncomplete`, the default durability setting may have written to the OS but not flushed to the physical disk. IndexedDB 3.0 lets you ask for stricter behaviour:

[code omitted]

- `strict` — commit only after changes are written to persistent storage.
- `relaxed` — commit once handed to the OS.
- `default` — browser chooses.

Use `strict` for the saves that matter (finish route, record step, save edit) and leave the frequent track-point writes on the default for performance. It is a hint; support varies.

**What is not persistent**

- It is per origin, per browser, per profile, per device. Chrome's copy is not visible to Safari; the phone's copy is not on the laptop. There is no built-in sync.
- Uninstalling the PWA may or may not delete its storage, depending on platform; don't rely on either outcome.
- Device backups are not a dependable route archive.
- Clearing "cookies and site data" removes it; clearing history alone usually does not.

**What this means for Sherpa**

Treat IndexedDB as a durable **working copy and outbox**, not as the archive:

1. On first recording, call `persist()` and show whether storage is protected or best-effort.
2. Save the draft after every step and every N track points; use `durability: 'strict'` for step/finish saves where supported.
3. Handle `QuotaExceededError` explicitly and offer export.
4. Export and sync early. The `.sherpa` file or the server copy is the real durability story; the phone is where work happens.
5. On iOS, "Add to Home Screen" improves both quota (roughly 60% of disk rather than 15%) and the chance of persistent mode.
6. Test the failure modes: kill the app mid-route, reboot, clear site data, fill storage. Recovery should be obvious, not silent.

**Bottom line:** restart-safe, yes. Eviction-proof, no — unless persistent mode is granted, and even then the user can still delete it. Design for sync and export.

**Assistant**

Agreed. IndexedDB is a browser capability the language should own, and the vocabulary transfers to any offline app. I've written the spec to `specs/allspeak-idb-plugin.md`.

**Shape**

- Domain `idb`, used as a prefix like `rest`: `idb open`, `idb put`, `idb get all`.
- Typed handles declared first, like `gmap Map`: `idb database DB`, `idb batch Batch`, `idb cursor C`, `idb blob B`.
- Declarative schema: build a schema in memory, then `idb open \`sherpa\` as DB using Schema` creates or upgrades it.
- CRUD, key/index queries with `where`, explicit range forms (`is`, `is between`, `is above`, `is below`, `is at least`, `is at most`).
- Batches for atomic multi-store writes.
- Cursors for large sets and in-place updates.
- Blob storage for photos.
- Storage API: `idb estimate storage`, `idb request persistence`, `idb check persistence`.
- Standard `or` / `on failure` clauses on every I/O command.

**The one non-obvious design decision** is batches. IndexedDB transactions auto-commit when their request queue empties.
